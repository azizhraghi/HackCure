SurgiGuard — l'histoire complète

Du boîtier ESP32 à l'équipe soignante : l'API SurgiGuard (.NET + MongoDB) porte les données, les agents IA les analysent, la famille est prévenue par l'API. Patiente fictive, pas un dispositif médical.

1

La patiente et son boîtier

API SURGIGUARD

Le compte, le code famille et le device_id du boîtier viennent de l'API. L'IA retrouve seule la patiente qui possède l'ESP32 (ESP32_001) : rien n'est saisi deux fois, et ses seuils (BPM min/max, SpO₂ min) sont ceux de l'API.

2

Le plan de soins devient les médicaments de l'app

IA D2API

Quand la patiente confirme son plan (documents → plan, voir la console), les médicaments sont poussés vers l'API : ce sont eux qui sonnent sur l'app Android (MoniteurAndroid) et dont l'observance est suivie. Le sens inverse existe aussi : une prise « prise » dans l'app Android remonte à l'agent médicaments.

Rééducation guidée par la caméra

IA D1-EESP32

Le moteur D1 construit les exercices pour cette patiente (chirurgie, jour post-op, facteurs de risque, limites du chirurgien), compte les répétitions, mesure l'amplitude et la tenue, et s'abstient quand la caméra ne voit pas la jambe. Tests de mouvement guidés

IA D1-D

Six tests courts, sur accord de la patiente (refuser ou arrêter = « non terminé », jamais « test raté »). Le moteur mesure, compare gauche/droite et les séances précédentes, et rapporte ce qu'il voit : jamais un diagnostic. Un écart notable devient une alerte « attention » pour le médecin, pas une urgence. Pas de test proposé si une alerte urgente est ouverte, et les symptômes déclarés passent par la porte d'urgence.
